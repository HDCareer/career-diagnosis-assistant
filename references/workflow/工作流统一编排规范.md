# SkillⅠ｜工作流统一编排规范

## 1. 职责分离

### A. Codex 与冻结 SkillⅠ 核心

冻结核心负责读取经授权的客户材料、自然语言归一化、差量补问和专业求职判断。只有编排器返回下列动作时，Codex 才能生成对应业务内容：

- `GENERATE_PRE_REPORT_CONTENT`：会前 JSON 与 Markdown；
- `CREATE_CONSULTATION_CONFIRMATION`：顾问确认表和状态为 `draft` 的内部纪要；
- `GENERATE_FINAL_CONTENT`：最终 JSON、Markdown、变更记录和行动清单。

冻结核心不负责状态写入、文件校验或直接调用 Renderer。

### B. 工作流编排器

编排器读取现有 `case_state.py` 的匿名状态，输出唯一下一步，登记已生成文件，执行合法状态推进，并只通过适配器触发渲染。repository 模式入口为 `workflow/workflow_orchestrator.py`；Plugin 模式入口为 `scripts/workflow_orchestrator.py`。它不读取简历、逐字稿或结构化纪要正文；顾问咨询总结只做 UTF-8、非空和基础完整性校验，不保存正文，不生成业务分析，不另建状态定义。

### C. Renderer 适配器

适配器验证报告阶段、输入和输出，记录技术日志及产物状态。它不会修改 JSON、Markdown、冻结核心或 Renderer。repository 模式入口为 `workflow/renderer_adapter.py`，并调度 `report_renderer/render_report.py`；Plugin 模式入口为 `scripts/renderer_adapter.py`，并调度 `assets/report_renderer/render_report.py`。Plugin 模式不得根据仓库根目录寻找 Renderer。

禁止事项：Python 不得代替冻结核心做判断；Renderer 失败不得触发内容再生成；Codex 不得绕过状态机直接调用 Renderer。

## 2. 唯一下一步动作

| 动作 | 顾问可见含义 |
| --- | --- |
| `CHECK_INTAKE` | 正在检查会前材料。 |
| `REQUEST_MISSING_INPUT` | 需要补充会前材料。 |
| `GENERATE_PRE_REPORT_CONTENT` | 可以生成会前诊断初版。 |
| `RENDER_PRE_REPORT` | 可以生成会前可阅读报告。 |
| `WAIT_FOR_CONSULTATION` | 等待完成咨询并提供逐字稿、结构化纪要或顾问咨询总结。 |
| `CREATE_CONSULTATION_CONFIRMATION` | 需要整理顾问确认表。 |
| `WAIT_FOR_CONSULTANT_CONFIRMATION` | 等待顾问确认咨询纪要。 |
| `GENERATE_FINAL_CONTENT` | 可以生成最终报告和行动清单。 |
| `RENDER_FINAL_BUNDLE` | 可以生成正式最终交付文件。 |
| `RETRY_PRE_RENDER` | 会前内容已保留，只重试渲染。 |
| `RETRY_FINAL_RENDER` | 最终内容已保留，只重试最终交付包。 |
| `CASE_COMPLETE` | 本次 Case 已完成。 |
| `STATE_ERROR` | 状态或文件有冲突，需先修复。 |

编排器会在没有业务判断的前提下，自动应用已满足门槛的合法阶段流转；不会自动重新生成任何内容。

## 3. 状态与动作规则

| Case 状态 | 条件 | 唯一动作 |
| --- | --- | --- |
| `new_case` | 尚未做材料检查 | `CHECK_INTAKE` |
| `new_case` | 已检查且缺材料 | 推进到 `intake_incomplete`，`REQUEST_MISSING_INPUT` |
| `new_case` / `intake_incomplete` | 材料完整 | 推进到 `pre_analysis_ready`，`GENERATE_PRE_REPORT_CONTENT` |
| `pre_analysis_ready` | 会前内容缺失 | `GENERATE_PRE_REPORT_CONTENT` |
| `pre_analysis_ready` | Renderer 可重试错误 | `RETRY_PRE_RENDER` |
| `pre_analysis_ready` | 会前内容齐全、HTML 未齐 | `RENDER_PRE_REPORT` |
| `pre_analysis_ready` | 会前交付齐全 | 推进到 `awaiting_consultation`，`WAIT_FOR_CONSULTATION` |
| `awaiting_consultation` | 未收到逐字稿、结构化纪要或顾问咨询总结 | `WAIT_FOR_CONSULTATION` |
| `awaiting_consultation` | 已收到逐字稿、结构化纪要或顾问咨询总结 | `CREATE_CONSULTATION_CONFIRMATION` |
| `consultation_notes_draft` | 等待确认 | `WAIT_FOR_CONSULTANT_CONFIRMATION` |
| `final_generation_ready` | 最终内容缺失 | `GENERATE_FINAL_CONTENT` |
| `final_generation_ready` | Renderer 可重试错误 | `RETRY_FINAL_RENDER` |
| `final_generation_ready` | 最终内容齐全、交付文件未齐 | `RENDER_FINAL_BUNDLE` |
| `final_generation_ready` | 最终交付齐全 | 推进到 `completed`，`CASE_COMPLETE` |
| `completed` | — | `CASE_COMPLETE` |

无效状态、非 Renderer 的内容校验错误或状态与文件冲突都返回 `STATE_ERROR`。

## 4. 文件登记与阶段校验

所有登记文件必须位于当前 Case 目录、存在且非空。会前 JSON 必须为 `pre_consultation_report_data.json`，并满足：

```text
report_meta.report_stage = pre_consultation
source_register.consultation_confirmation_status = not_started
```

最终 JSON 必须为 `final_customer_report_data.json`，行动清单必须为 `post_consultation_action_checklist.md`，并满足：

```text
report_meta.report_stage = post_consultation_final
source_register.consultation_confirmation_status = confirmed
```

咨询材料分三类独立登记：

- `consultation_transcript`：咨询逐字稿；只检查存在性和非空，不读取正文。
- `consultation_structured_notes`：结构化咨询纪要；只做 UTF-8、非空和基础完整性校验。
- `consultant_summary`：顾问咨询总结；缺少逐字稿时可作为降级路径，必须是 UTF-8 文本、非空，并通过基础完整性校验。不得登记为逐字稿。

当 `consultation_transcript`、`consultation_structured_notes` 或 `consultant_summary` 至少一个为 `received` 时，才允许生成顾问确认表。若只有顾问总结，内部纪要和变更记录必须保留“信息来源为顾问总结”的审计痕迹，不得改写成客户逐字原话；原话追溯、语境复核和矛盾核验能力降低。

内部纪要必须含明确标记 `consultation_confirmation_status: draft` 或 `confirmed`；状态中只有一个“当前有效内部纪要”指针，Case 目录同时保留草稿和已确认的实际文件，不覆盖历史草稿。进入 `confirmed` 时必须同时登记 `confirmed_consultation_snapshot`，作为会前信息与咨询变化合并后的唯一快照。

最终内容登记前必须全部满足：

- 会前初版 JSON 已存在；
- 原始简历或完整输入材料、归一化会前材料均已登记；
- 至少一种咨询原始材料已登记；
- consultation confirmation 已 confirmed；
- `confirmed_consultation_snapshot` 已登记并通过结构校验；
- 无阻塞冲突。

## 5. Renderer 调度契约

适配器只使用参数列表调用 Renderer，入口由当前运行模式解析得到。

repository 模式解析为：

```text
python report_renderer/render_report.py --data <JSON> --out <Case目录内输出目录> --no-pdf --no-index
```

Plugin 模式不得直接调用仓库根目录 `report_renderer/`。它必须通过 `scripts/workflow_orchestrator.py render-pre|render-final|retry-render` 进入 `scripts/renderer_adapter.py`，再由适配器解析到包内 `assets/report_renderer/render_report.py`。

最终 bundle 在同一次调用中额外传入 `--checklist <行动清单.md>`。会前输出目录固定为 `02_pre_consultation/`，最终输出目录固定为 `04_final_delivery/`。适配器依据 Renderer 固定文件名验证 HTML，不通过“最新文件”猜测结果。

正式工作流只交付 HTML：会前要求 `pre_consultation_report.html`，最终要求 `final_customer_report.html` 和 `post_consultation_action_checklist.html`。`pre_report_pdf`、`final_report_pdf` 和 `action_checklist_pdf` 仅为历史兼容字段或客户自行用浏览器另存为 PDF 的结果，不参与状态推进，不得生成空白 PDF、占位 PDF 或伪造 PDF ready 状态。

Renderer 日志只写 `<CASE_DIR>/logs/renderer-YYYYMMDD-HHMMSS.log`，只包含匿名编号、bundle、相对路径、退出码和经压缩的技术摘要；不记录客户正文或个人信息。

## 6. 失败与恢复

内容生成或内容校验失败，记录为 `content_generation` 或 `content_validation`，不调用 Renderer。修正已生成文件后必须重新登记对应内容，登记校验通过才会清除该内容校验错误。Renderer 失败时保留 JSON 和 Markdown，将对应 HTML 标记为 `failed`，写入 `renderer_pre` 或 `renderer_final` 的可重试错误；后续只能使用相同 bundle 的 `retry-render`。重试不会改业务阶段，也不会重新生成专业内容。
