# SkillⅠ v3.0｜咨询后报告更新规范

## 使用目标

本文件规定如何用已归一化且经顾问确认的咨询纪要，将会前诊断初版更新为咨询后最终报告。目标是更新真实发生变化的内容，而不是无理由重写整份报告。

## 最终报告强制门槛

只有同时存在会前初版、完整简历、归一化会前材料、至少一种原始咨询材料、归一化后的 `consultation_confirmation`、`consultation_confirmation_status: confirmed`、`confirmed_consultation_snapshot`，且没有阻塞冲突时，才可进入最终报告更新。

`not_started` 表示尚未进入咨询后流程；`draft` 表示纪要仍待顾问确认。两者均不得生成最终报告、咨询后行动清单、变更记录或最终 HTML。即使状态为 `confirmed`，仍必须检查会前初版、完整简历、归一化会前材料、原始咨询材料、归一化咨询纪要、已确认合并快照和未知信息标注是否齐全。

逐字稿、顾问记录或初步纪要首先只能将状态从 `not_started` 变为 `consultation_confirmation_status: draft`，并生成确认模板。输出该模板后必须停止，不得生成最终报告、咨询后行动清单或内部变更记录。状态为 `draft` 时固定提示：

> 当前咨询纪要仍处于待确认状态。请顾问完成补充、修正或明确确认后，再生成咨询后最终报告。

顾问填写或修改模板后返回，或明确回复“以上咨询纪要已确认”且没有提出修改时，才能设置为 `confirmed`。顾问观点和客户明确确认必须保持分开。

## 信息优先级

按以下顺序处理信息：

1. 客户在咨询中明确确认的信息，优先于售前阶段的模糊回答。
2. 简历中的客观事实，除非客户明确纠正，否则不得覆盖。
3. 顾问判断属于专业判断，不得改写成客户事实。
4. 信息冲突且未得到确认时，继续标记为未确认。
5. 最终报告只更新受咨询影响的内容，不得无理由全面改写。
6. 主方向发生变化时，必须记录变化原因。
7. 已解决的信息不得在最终报告中继续显示为待确认。
8. 新增经历必须注明来源于咨询确认，不得补造结果数据。

## 更新流程

1. 读取会前初版、完整简历、归一化会前材料、原始咨询材料、归一化咨询纪要和 `confirmed_consultation_snapshot`；确认状态必须为 `confirmed`。
2. 将每条咨询信息归入 `customer_confirmed_facts`、`customer_stated_preferences`、`customer_accepted_options`、`consultant_judgements`、`jointly_agreed_decisions`、`consultant_recommended_actions` 或 `jointly_agreed_actions`。
3. 以会前已确认边界为基线执行增量合并；变化状态只能是 `unchanged`、`added`、`modified`、`revoked`、`superseded` 或 `unresolved`。
4. 保留未被纠正的简历事实；对冲突而未确认的信息不做覆盖。
5. 只更新受影响的报告章节和对应 JSON 字段。
6. 从最终报告删除已解决的“咨询中需要确认”标记；保留真正仍未知的信息。
7. 重新执行章节去重、方向分类和跨章节一致性检查。
8. 输出 `final_customer_report_data.json` 和内部 `consultation_change_log.md`。
9. 由确定性物化器从最终 JSON 生成 `final_customer_report.md` 和 `post_consultation_action_checklist.md`，确认最终报告数据、物化正文、已确认咨询纪要、合并快照和内部变更记录均存在且一致后，才进入 Renderer。

## 咨询后行动清单的依据

生成咨询后行动清单前，必须确认最终报告数据、确定性物化的最终报告正文、已确认的咨询纪要和内部变更记录均已存在。

行动清单的客户内容只允许从 `final_customer_report_data.json` 和与其一致的 `final_customer_report.md` 中提炼。已确认咨询纪要和 `consultation_change_log.md` 只用于一致性校验、确认信息来源和防止遗漏，不得绕过最终报告直接新增行动、方向或结论。

如果最终 JSON 与物化 Markdown 不一致，必须先修正最终 JSON，不能直接手写行动清单覆盖。行动清单不得根据逐字稿增加最终报告未采纳的方向，不得根据变更日志恢复已删除或否定的会前方向；其剩余未知、主攻、相邻备选、行动脚手架和重新评估信号必须与最终报告一致。

最终更新必须同时处理 0.3.0 内容契约：

1. `decision_snapshot.core_question_answers` 逐项回答最多 3 个核心问题。
2. `source_register.critical_evidence_status` 区分客户自述、顾问总结、顾问判断、材料支持和独立验证。
3. `candidate_context.current_assets`、`future_potential`、`planned_not_current` 分开记录。
4. `salary_assessment` 区分客户期待与顾问现实性判断；未使用外部样本时不得生成市场数字。
5. 高优先级差距形成最多 3 张修复卡。
6. `priority_action_scaffolds` 形成 0—3 个按依赖排序的行动脚手架，不为了凑数生成。
7. `source_register.consultation_truth` 强制区分客户事实、客户偏好、客户可接受选项、顾问判断、共同定案、顾问建议行动和共同确认行动。
8. `source_register.confirmed_consultation_snapshot` 是最终阶段唯一合并快照；最终报告不得从未确认顾问总结或逐字稿自由投影。

已确认咨询纪要中的 0.3.0 新字段必须进入最终 JSON 的现有承载位：

| 已确认字段 | 最终 JSON 更新规则 |
|---|---|
| `salary_reality_judgement` | 写入 `recruitment_path_salary_and_roadmap.salary_assessment`；客户薪资期待只进入 `customer_ideal_target` 或 `customer_minimum_boundaries`，不得进入外部市场参考。 |
| `confirmed_gap_repair_strategies` | 写入 `improvement_priorities` 的修复卡字段；最多 3 项，保留处理原则、简历策略、面试框架、证据准备、避免措辞、剩余风险和重新评估条件。 |
| `transition_reassessment_criteria` | 写入相关方向的 `activation_condition` / `reassessment_condition`，并同步到 `main_direction_preparation.adjustment_signals` 或行动清单复评信号。 |
| `confirmed_priority_actions` | 写入 `recruitment_path_salary_and_roadmap.priority_action_scaffolds`；顾问确认行动、顺序、产出和依赖，Codex 在最终生成时补齐第一步、内容框架、投入、完成检查和常见错误。 |

顾问没有形成明确判断时，最终 JSON 必须保留“未形成明确判断”对应的证据边界，例如薪资判断使用 `insufficient_basis`；不得强行升级成确定结论。没有外部样本时，`external_market_reference.status` 必须为 `not_used`。

## 内部变更记录

`consultation_change_log.md` 必须包含以下结构：

```yaml
consultation_change_log:
  corrected_information:
    - item:
      affected_sections:
      source: consultation_confirmed
  newly_added_information:
    - item:
      affected_sections:
      source: consultation_confirmed
  direction_changes:
    - previous_direction:
      final_direction:
      reason:
      affected_sections:
  removed_assumptions:
    - item:
      reason:
  resolved_unknowns:
    - item:
      final_status:
  remaining_unknowns:
    - item:
      impact:
      where_shown:
```

变更记录只供内部审计，不得直接复制到 `final_customer_report.md`，更不得在客户报告中展示“初版错误”“顾问修正”等内部过程。

## 章节更新映射

| 咨询确认信息 | 应更新位置 |
|---|---|
| 地区、城市、岗位、平台、工作方式或主动排除 | 02、01 摘要、06、09 |
| 新增经历或纠正事实 | 04、03、07（仅经历映射）、09 |
| 主攻或相邻备选改变 | 01、03、05、06、07、08、09 和变更记录 |
| 已解决的未知 | 02 和 09 中移除待确认标记；记录到变更日志 |
| 仍未解决的资格/边界 | 02、05（如影响决策）、09 和行动清单 |
| 薪资现实性判断 | 08 的 `salary_assessment`；09 保留证据边界 |
| 差距修复策略 | 05 的高优先级修复卡；必要时同步 07 的准备方案 |
| 方向复评标准 | 06 的方向启用或复评条件；07 的调整信号；行动清单复评信号 |
| 咨询同意的行动 | 08 的 30/60/90 路线和 `priority_action_scaffolds`；行动清单只从最终报告提炼 |

## 禁止做法

不得因咨询后生成最终版而虚构经历、量化成果、市场事实、资格结论、实时岗位、薪资承诺或结果承诺。不得把客户明确排除的销售、轮岗、外派等方向写成诊断性暂不建议方向。

不得把顾问确认纪要、顾问总结或客户表示可由导师佐证自动写成“已核实”“已验证”或“已证实”。不得把尚未入学、计划考证、计划实习、计划作品等写成当前竞争力资产。
